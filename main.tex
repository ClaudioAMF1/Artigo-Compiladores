\begin{abstract}
Large Language Models (LLMs) have shown remarkable performance in software engineering tasks, including code transformation and optimization. In dynamic languages such as Python, classical compiler optimizations are historically constrained by dynamic typing, late binding, and reflection -- factors that shrink the decision space available to a static compiler. This paper investigates the limits and possibilities of using LLMs as an auxiliary component to the Python compilation process, proposing a hybrid architecture (AST-based static analysis + LLM + test-based validation) evaluated on the public HumanEval dataset (OpenAI), comprising 164 Python problems with unit tests. We conduct a paired comparison of \textbf{four optimization back-ends}: a deterministic AST-rule baseline and \textbf{three LLMs from distinct providers and families} (Gemini 2.5 Flash Lite, Llama 3.3 70B via Groq, and GPT-4o-mini via GitHub Models). Results quantify a structured trade-off: the baseline preserves semantics in 100\% of cases but its median speedup is statistically indistinguishable from $1.0\times$ (95\% bootstrap CI $[0.997;~1.008]$). Across the LLMs, strong heterogeneity is observed: Gemini improves 54.3\% of problems with a significant median speedup ($1.138\times$, CI $[1.071;~1.220]$) and a 6.1\% hallucination rate; GPT-4o-mini improves 37.2\% with a median of $1.018\times$ (not significant) and a 17.7\% hallucination rate; Llama 70B improves 27.4\% with a median of $0.976\times$ (not significant, in fact below 1) and a 23.2\% hallucination rate. This refutes the naive thesis ``LLMs beat the baseline'' and establishes a more precise one: \emph{model choice matters as much as the decision to use an LLM} -- only the LLM best calibrated for the code-transformation task delivers a statistically significant median gain, while LLMs from other families exhibit hallucination rates that neutralize their improvements. The findings support hybrid architectures with mandatory semantic validation and empirical model selection.
\end{abstract}

\section{Introduction}

The growing adoption of Python in domains such as data science, machine learning, and automation has reinforced the importance of its runtime performance. Despite this, the reference interpreter CPython provides relatively modest optimizations compared to mature compilation toolchains such as LLVM or GCC \cite{DBLP:books/mk/CooperT11}. This gap largely stems from features of the language itself: dynamic typing, late binding, monkey patching, and the ability to introspect and modify programs at runtime \cite{DBLP:conf/pldi/RichardsLBV10}.

In parallel, Transformer-based Large Language Models (LLMs) have been successfully employed in code transformation and optimization tasks \cite{DBLP:journals/corr/abs-2309-07062,DBLP:journals/corr/abs-2407-02524,DBLP:journals/csur/AllamanisBDS18}. Recent work has shown that LLMs can suggest code transformations that yield substantial runtime improvements in Python \cite{DBLP:journals/corr/abs-2302-07867}. The central hypothesis of this work is that LLMs can act as a hybrid component, complementing the optimization phases of a Python compiler, operating both at the source-code and bytecode levels to mitigate the bottlenecks imposed by the language's dynamism. To avoid drawing conclusions from a single model, we run the proposed pipeline in \textbf{four paired configurations} over the 164 HumanEval problems: a deterministic AST-rule baseline and three LLMs from distinct providers and families -- \textbf{Gemini 2.5 Flash Lite} (Google), \textbf{Llama 3.3 70B} (Meta, via Groq), and \textbf{GPT-4o-mini} (OpenAI, via GitHub Models).

This paper addresses the following research question: \textit{what are the limits and possibilities of using LLMs to optimize Python code in the context of a compilation pipeline, given the constraints imposed by a dynamic language?}

The contributions of this work are: (i) a critical survey of the state of the art on LLMs applied to code optimization, with a focus on Python; (ii) a systematic analysis of the limits imposed on static optimizations by the language's dynamism; (iii) the proposal and implementation of a hybrid architecture (AST-based static analysis + interchangeable LLM + test-based validation) operating on the public HumanEval dataset and supporting multiple providers (Google, Groq, OpenAI/GitHub Models, direct OpenAI, Together); and (iv) a paired and \textbf{multi-model} empirical study over the 164 HumanEval problems, comparing three LLMs from distinct families against a deterministic AST-rule optimizer and quantifying, with significance tests (paired \textit{t}-test, 95\% bootstrap CI), semantic preservation, hallucination rate, performance gains, and regressions.

The remainder of the paper is organized as follows. Section~\ref{sec:fundamentacao} presents the theoretical background on dynamic-language compilation and LLMs for code. Section~\ref{sec:relacionados} discusses related work. Section~\ref{sec:metodologia} describes the proposed architecture, the foundation models, and the dataset. Section~\ref{sec:resultados} presents the experimental results of the deterministic baseline and the Gemini back-end, with statistical significance tests. Section~\ref{sec:discussao} discusses limits and possibilities. Section~\ref{sec:ameacas} lists threats to validity. Section~\ref{sec:conclusao} presents the conclusions and outlines future work.

\section{Theoretical Background}
\label{sec:fundamentacao}

\subsection{Dynamic languages}
Dynamic languages are characterized by the absence of type checking at compile time and by late binding of names, methods, and attributes. Ousterhout's seminal taxonomy of scripting languages \cite{DBLP:journals/computer/Ousterhout98} positioned this model as a deliberate engineering trade-off: flexibility -- the programmer can alter a program's structure at runtime, redefine class methods (monkey patching), and introspect any object -- in exchange for the predictability needed for global static analyses defined in the classical compiler literature \cite{DBLP:books/aw/AhoLSU06,DBLP:books/mk/CooperT11}.

The empirical literature has measured the practical magnitude of this dynamism. Richards et al.~\cite{DBLP:conf/pldi/RichardsLBV10}, in a landmark study published at PLDI~2010, observed that real-world JavaScript programs systematically violate the very assumptions made by static analyses and JIT compilers -- e.g., extensive runtime use of \texttt{eval}, dynamic prototype modification, and polymorphic call sites. For Python, Holkner and Harland \cite{DBLP:conf/acsc/HolknerH09}, in an ACSC~2009 study of widely used applications, found that the most aggressively dynamic constructs (\texttt{exec}, class mutation, attribute injection) appear predominantly during initialization phases but rarely in steady-state hot loops, suggesting that a meaningful subset of code could in principle be specialized. Complementing this picture, {\AA}kerblom and Wrigstad \cite{DBLP:conf/dls/AkerblomW15} quantified the polymorphism of Python programs at DLS~2014 and showed that, although the language permits unrestricted polymorphism, the majority of call sites in benchmark suites are effectively monomorphic at runtime -- a property that JIT-based implementations explicitly exploit.

\subsection{Python and performance}
CPython, the reference implementation of the language, is a stack-based virtual machine that interprets bytecode produced by a classical pipeline: lexical and syntactic analysis, AST construction, control-flow graph generation, and bytecode emission \cite{DBLP:books/aw/AhoLSU06}. Historically, the compiler performs few optimizations, limited to constant folding and folding of simple expressions \cite{DBLP:books/aw/AhoLSU06}. Starting with CPython 3.11, the specializing adaptive interpreter introduced by PEP 659 \cite{pep659} enabled dynamic specialization of bytecode instructions based on types observed at runtime, importing into CPython ideas previously confined to JIT implementations.

The main performance bottlenecks in Python are well characterized \cite{DBLP:conf/acsc/HolknerH09,DBLP:conf/dls/AkerblomW15}: (i) interpreted loops, due to per-iteration overhead of the virtual machine; (ii) heavy object allocation, due to the language's primitive types being full objects; and (iii) dynamic dispatch, stemming from runtime method resolution. Alternative implementations attempt to bypass dynamism through different strategies: \textbf{PyPy} \cite{DBLP:conf/icooolps/BolzCFR09} uses a meta-tracing JIT to specialize hot paths on observed types; \textbf{Numba} \cite{DBLP:conf/sc/LamPS15} compiles annotated numerical kernels to LLVM IR; and \textbf{Cython} \cite{DBLP:journals/cse/BehnelBCDSS11} statically translates type-annotated Python to C extension modules. All three trade some of Python's expressiveness for native-level performance.

Performance issues and optimization opportunities have been studied at the empirical software-engineering level as well. Selakovic and Pradel \cite{DBLP:conf/icse/SelakovicP16}, at ICSE~2016, conducted a large-scale empirical study of performance issues in JavaScript projects and identified recurrent anti-patterns -- such as inefficient choice of data structure, redundant property accesses, and avoidable object allocations -- that are largely transferable to Python given the structural similarities between the two languages. Nistor et al.~\cite{DBLP:conf/msr/NistorJT13}, at MSR~2013, examined how performance bugs are discovered and fixed in practice in large open-source projects, observing that they take substantially longer to detect than functional bugs and frequently require non-local reasoning that goes beyond compile-time analysis.

\subsection{Language Models (LLMs)}
Modern language models are built on the Transformer architecture \cite{DBLP:conf/nips/VaswaniSPUJGKP17}, whose self-attention mechanism enabled scaling to billions of parameters. Brown et al.~\cite{DBLP:conf/nips/Brown0MRSKDNSSAA20} demonstrated with GPT-3 that, at sufficient scale, these models acquire emergent few-shot learning abilities without task-specific fine-tuning. The application of this paradigm to source code was systematized by Chen et al.~\cite{DBLP:journals/corr/abs-2107-03374} with Codex and the HumanEval benchmark, extended to program synthesis at scale by Austin et al.~\cite{DBLP:journals/corr/abs-2108-07732} with the MBPP benchmark, and developed further by encoder representations such as CodeBERT \cite{DBLP:conf/emnlp/FengGTDFGS0LJZ20} and open code-specialized generative models such as Code Llama \cite{DBLP:journals/corr/abs-2308-12950} -- the lineage of the Llama family evaluated in this work.

Recent surveys have mapped the breadth of LLM applications in software engineering. Fan et al.~\cite{DBLP:conf/icse/FanGHLSYZ24}, in their ICSE~2024 Future-of-SE paper, identify code generation, repair, summarization, testing, and optimization as core tasks where LLMs already match or exceed traditional approaches in several benchmarks. Hou et al.~\cite{DBLP:journals/tosem/HouZLYWLLLGW24}, in a systematic literature review published at ACM TOSEM in 2024, classify over 200 papers along training paradigms, prompting strategies, and evaluation methodologies, providing a structural map of the field. In the optimization sub-area specifically, the broader machine-learning-for-code literature \cite{DBLP:journals/csur/AllamanisBDS18} and recent benchmark frameworks \cite{DBLP:journals/corr/abs-2407-02524} confirm that LLMs are competitive with handcrafted heuristic compilers for selecting and ordering optimization passes.

Unlike a classical compiler, an LLM operates probabilistically, providing no a priori guarantee of semantic equivalence; in return, it can apply high-level transformations that rely on broad algorithmic knowledge, beyond the reach of static heuristics. This property makes LLMs especially promising for dynamic languages -- precisely where classical compilers face their largest barriers.

\subsection{Code optimization}
The classical compiler literature \cite{DBLP:books/aw/AhoLSU06,DBLP:books/mk/CooperT11} organizes optimizations into three levels of granularity, all of which remain relevant when an LLM is introduced as a candidate generator: (i) \textbf{micro-optimizations}, which act on individual instructions or small fragments (e.g., operator replacement, constant folding); (ii) \textbf{structural refactoring}, which reorganizes algorithms or data structures (e.g., memoization, vectorization, data-structure substitution); and (iii) \textbf{parallelization}, which exploits concurrent execution on multiple cores. Standard evaluation metrics are \textbf{execution time}, \textbf{memory usage}, and, secondarily, \textbf{readability} and maintenance cost of the transformed code -- the latter increasingly emphasized in empirical studies of optimization in real-world software \cite{DBLP:conf/icse/SelakovicP16,DBLP:conf/msr/NistorJT13}. In Python, given the GIL and the VM overhead, the most substantial gains typically come from the second level, where LLMs are particularly competent.

\subsection{Limits imposed by dynamism}
The characteristics of dynamic languages constrain classical static optimizations:
\begin{itemize}
  \item \textbf{Dynamic typing:} a variable's type can change throughout execution, hampering specialization and inline caching \cite{DBLP:conf/pldi/RichardsLBV10}.
  \item \textbf{Late binding:} method and function resolution happens at runtime, ruling out aggressive static inlining \cite{DBLP:conf/dls/AkerblomW15}.
  \item \textbf{Reflection and metaprogramming:} constructs such as \texttt{getattr}, \texttt{setattr}, \texttt{eval}, and \texttt{exec} can alter the running program, breaking global analyses \cite{DBLP:conf/acsc/HolknerH09}.
  \item \textbf{Monkey patching:} the ability to replace class attributes at runtime invalidates guarantees about method tables.
  \item \textbf{GIL:} the Global Interpreter Lock constrains real parallelism, imposing specific choices on the compiler.
\end{itemize}

These factors define what we call the \textbf{static optimization frontier}: a set of transformations that conventional compilers cannot apply without additional assumptions about program behavior. Crossing this frontier without abandoning correctness is precisely the role that LLMs, combined with a test-based validation harness, may play in a modern Python compilation pipeline -- a direction supported both by recent empirical literature on LLMs in software engineering \cite{DBLP:conf/icse/FanGHLSYZ24,DBLP:journals/tosem/HouZLYWLLLGW24} and by the experimental evidence presented in Section~\ref{sec:resultados}.

\section{Related Work}
\label{sec:relacionados}

Cummins et al.~\cite{DBLP:journals/corr/abs-2309-07062} showed that an LLM trained on a corpus of LLVM-IR code can predict sequences of optimization passes that significantly reduce the size of generated code. The work was later extended in the \textit{Meta Large Language Model Compiler}, a family of models trained on 546 billion tokens of IR and assembly, explicitly aimed at optimization tasks \cite{DBLP:journals/corr/abs-2407-02524}.

Shypula et al.~\cite{DBLP:journals/corr/abs-2302-07867} introduced the \textit{Performance Improving Edits} (PIE) dataset, composed of program pairs (slow / fast versions) derived from the IBM Project CodeNet, with extensive unit tests. The work showed that models such as GPT-3.5 fine-tuned with retrieval, performance-conditioning, and self-play strategies can achieve average speedups of up to $6.86\times$ in competitive code optimization tasks.

A second line of work makes the generation process iterative by feeding execution or self-assessed feedback back to the model. Madaan et al.~\cite{DBLP:journals/corr/abs-2303-17651} proposed \textit{Self-Refine}, in which a single LLM alternately produces an output and critiques it, improving quality across diverse tasks without additional training. Chen et al.~\cite{DBLP:journals/corr/abs-2304-05128} specialized this idea to code with \textit{Self-Debug}, showing that an LLM that inspects execution results and error messages can correct its own programs. These feedback-driven approaches are the conceptual basis for the validation-and-retry loop in our pipeline: rather than trusting a single LLM response, we execute the candidate against the official tests and treat any failure as a discard signal. The broad applicability of LLMs to source code itself rests on the observation that software is highly repetitive and predictable -- the ``naturalness'' hypothesis of Hindle et al.~\cite{DBLP:conf/icse/HindleBSGD12} -- which motivated a generation of learned code models, from encoder-decoder architectures such as CodeT5 \cite{DBLP:journals/corr/abs-2109-00859} to large open code models such as Code Llama \cite{DBLP:journals/corr/abs-2308-12950}, DeepSeek-Coder \cite{DBLP:journals/corr/abs-2401-14196}, and StarCoder~2 \cite{DBLP:journals/corr/abs-2402-19173}.

In a complementary methodological direction, \textit{DocAgent} \cite{DBLP:journals/corr/abs-2504-08725} introduces a multi-agent system for automated code documentation generation that combines AST-based static analysis, construction of a dependency graph among components (functions, classes, methods), topological traversal for incremental context building, and specialized agents (\textit{Reader}, \textit{Searcher}, \textit{Writer}, \textit{Verifier}, \textit{Orchestrator}). Although the target problem is docstring generation rather than optimization, two aspects of the DocAgent architecture transfer directly to the pipeline proposed here: (a) the use of the AST as a canonical representation to extract entities and their dependencies, preventing the LLM from operating on the source code as opaque text; and (b) the presence of a \textit{Verifier} agent that factually validates the LLM's output against the repository, mitigating hallucinations. This pattern is analogous to the test-based validation module adopted in our methodology (Section~\ref{sec:metodologia}).

The use of machine learning for automatic code transformation predates the modern LLM era. Silva \cite{silva2020ferramenta}, in a 2020 bachelor's monograph at the Universidade Federal Rural do Semi-{\'A}rido (UFERSA), proposed a tool that uses an LSTM recurrent neural network to suggest token-level corrections for syntactic errors in introductory programming code, operating on a tokenized representation produced by ANTLR. That work is a direct precursor to ours along two axes and a useful contrast point along a third. Methodologically, both pipelines tokenize the source program and let a neural model predict transformations on the token stream; architecturally, however, Silva's LSTM is bounded by relatively local context, while modern Transformer-based LLMs leverage attention over much longer spans, enabling the algorithmic-level transformations (memoization, closed-form replacements, primitive substitutions) that our experiments confirm in Section~\ref{sec:llmvsbase}. The third axis -- task -- is complementary rather than overlapping: Silva targets \emph{syntactic correctness} for novice code, whereas this work targets \emph{performance optimization} for code that is already syntactically and semantically correct. The combined picture suggests that the broader research agenda of \textit{neural code transformation} has matured from local repair toward global, performance-aware rewriting as model architectures and training data have scaled.

The recent empirical software-engineering literature converges on three observations directly relevant to our methodology. First, pre-trained code models differ substantially among themselves: Niu et al.~\cite{DBLP:conf/icse/NiuLNCGL23}, at ICSE 2023, conducted a head-to-head evaluation of multiple pre-trained source-code models and observed effect sizes between models that exceeded the differences between fine-tuning strategies -- foreshadowing the model-choice-matters finding we report in Section~\ref{sec:llmvsbase}. Second, LLM outputs show systematic quality issues that demand explicit mitigation: Liu et al.~\cite{DBLP:journals/tosem/LiuLWTLLL24}, in ACM TOSEM 2024, characterized recurring code-quality problems in ChatGPT-generated Python code and proposed automated refinement strategies, while Mastropaolo et al.~\cite{DBLP:conf/icse/MastropaoloPGCSO23}, at ICSE 2023, showed that GitHub Copilot's outputs vary considerably under semantically equivalent prompt perturbations. Third, LLMs are nonetheless effective at code-transformation tasks beyond pure generation: Jiang et al.~\cite{DBLP:conf/icse/JiangLLT23}, at ICSE 2023, demonstrated that code language models substantially improve automated program repair, and Pan et al.~\cite{DBLP:conf/icse/PanIKSWMSPSJ24}, at ICSE 2024, dissected the bugs LLMs introduce while translating code between languages -- a closely related task to ours that confirms the necessity of test-based validation. Finally, Nam et al.~\cite{DBLP:conf/icse/NamMHVM24}, at ICSE 2024, found that LLMs measurably help developers understand unfamiliar code -- a usability dimension complementary to the runtime-performance focus of this work.

Taken together, these works indicate that LLMs are competitive -- and often complementary -- to classical compilers, especially when optimizations occur at a higher semantic or algorithmic level, and that architectures that couple static analysis (AST, dependency graphs) with a generation-with-verification loop tend to produce more reliable results than direct prompts over source code. The distinguishing feature of the present study is the combination of a \emph{paired, multi-model} comparison (three LLMs from distinct families plus a deterministic baseline) with a mandatory executable validation oracle, applied specifically to the under-studied setting of a dynamically typed language. Most prior work either evaluates a single model, targets a statically typed or intermediate representation, or omits a paired symbolic baseline that quantifies the marginal value of the LLM.

\section{Methodology and Proposed Architecture}
\label{sec:metodologia}

\subsection{Foundation Models}
To avoid conclusions biased by a single model, this work evaluates \textbf{three LLMs from distinct providers and families}, all accessed via free tier with no monetary cost:

\begin{itemize}
  \item \textbf{Gemini 2.5 Flash Lite} (Google): accessed via REST through Google AI Studio. Proprietary model with a compact architecture optimized for low latency.
  \item \textbf{Llama 3.3 70B} (Meta): accessed via the Groq API, which serves the open-weight model on specialized inference hardware. Open model with 70 billion parameters.
  \item \textbf{GPT-4o-mini} (OpenAI): accessed via GitHub Models (Microsoft), which offers a free tier for the OpenAI ecosystem via a PAT with the \texttt{Models:Read} scope. Proprietary model, mid-size class.
\end{itemize}

All three were configured with the same hyperparameters (temperature = $0.2$, max\_output\_tokens = $2048$) and received the same structured prompt, ensuring comparability. Each provider exposes an OpenAI-compatible SDK API or a simple REST endpoint, allowing transparent back-end interchangeability in the pipeline. For transient errors (HTTP 429/5xx, common in free tiers), the client implements exponential retry of up to 7 attempts with backoff of up to 60 s.

To isolate the effect of the LLM paradigm itself, we additionally implement a deterministic AST-based rule optimizer used as the \textbf{baseline}. The paired comparison between the baseline and the three LLMs allows three effects to be separated: (a) the gain of the symbolic vs.\ probabilistic paradigm, (b) variation across distinct LLM families, and (c) the effect of the specific model choice within the LLM paradigm.

\subsection{Dataset}
As the research subject, we use \textbf{HumanEval} \cite{DBLP:journals/corr/abs-2107-03374}, a public dataset maintained by OpenAI and available in an open Git repository\footnote{\url{https://github.com/openai/human-eval}}. HumanEval comprises 164 Python programming problems, each containing: (i) a header with the signature, docstring, and examples; (ii) a canonical solution (\texttt{canonical\_solution}); and (iii) a function \texttt{check(candidate)} containing the assertions that define functional correctness. HumanEval was chosen due to its broad adoption as a reference in Code LLM research, the quality of its unit tests, and the fact that it is 100\% Python. As an auxiliary repository of optimization examples (few-shot), the PIE dataset \cite{DBLP:journals/corr/abs-2302-07867} remains a source of (slow, fast) pairs for future extensions.

\subsection{Pipeline Architecture}
The proposed architecture is organized in five modules, described below:

\begin{enumerate}
    \item \textbf{Ingestion Module:} reads the 164 HumanEval problems directly from the official \texttt{HumanEval.jsonl.gz} file, extracting \texttt{prompt}, \texttt{canonical\_solution}, \texttt{entry\_point}, and \texttt{test}.
    \item \textbf{Static Analysis Module:} builds the AST of the full code (\texttt{prompt + canonical\_solution}) via the standard \texttt{ast} module and extracts numerical features: number of functions, loops, maximum nesting depth, function calls, recursive calls to the entry point, comprehensions, and presence of type annotations.
    \item \textbf{Optimization Module:} accepts interchangeable back-ends via a configuration parameter: (a) \texttt{gemini}/\texttt{groq}/\texttt{github\_models} -- forwards the code and the features to the corresponding LLM through a structured prompt that demands strict signature and semantics preservation; (b) \texttt{rule\_based} -- applies a deterministic sequence of AST transformations: R1 memoization via \texttt{functools.lru\_cache}, R2 manual summation replaced by \texttt{sum()}, R4 \texttt{frozenset} for membership tests, and R5 \texttt{join} for string concatenation in a loop.
    \item \textbf{Validation Module:} compiles the returned code, executes the \texttt{check(candidate)} function of HumanEval under \texttt{SIGALRM} with a 10-second timeout, and discards the transformation if any assertion fails or an exception is raised.
    \item \textbf{Benchmark Module:} builds a reproducible workload from the very \texttt{candidate(\ldots)} calls present in the official problem test, runs the workload \textbf{200 times in each of 5 repetitions}, and reports the minimum time (to minimize noise). The speedup is defined as $s = t_\text{orig}^\text{min}/t_\text{opt}^\text{min}$.
\end{enumerate}

The complete pipeline can be interpreted as a feedback-assisted loop: failures detected in the validation module can be re-introduced into the prompt in a strategy analogous to self-refine.

\subsection{The Deterministic Rule Set}
\label{sec:rule_set}

The baseline optimiser is intentionally simple, so that it serves as an honest lower bound: a transformation either matches an exact syntactic pattern, or it is not applied. Each rule is implemented as an \texttt{ast.NodeTransformer} that rewrites a sub-tree only when its precondition holds; otherwise the original node is returned unchanged, guaranteeing semantic preservation by construction for the patterns it recognises. Four rules are implemented.

\paragraph{R1 -- Memoization} If the entry-point function contains a recursive call to itself (detected by an \texttt{ast.NodeVisitor} that flags any \texttt{Call} whose callee name equals the entry point), the rule prepends the \texttt{@functools.lru\_cache(maxsize=None)} decorator and inserts the corresponding import if absent. The precondition is $f.\mathit{nrec} > 0$. This is the highest-impact rule, turning exponential recursion into linear amortised time.

\paragraph{R2 -- Builtin summation} The rule matches the exact pattern of an accumulator initialised to zero followed by a \texttt{for} loop whose body is a single \texttt{acc += expr} (or \texttt{acc = acc + expr}) statement, and rewrites it as \texttt{acc = sum(expr for var in iter)}. The precondition is the presence of the two-statement init-loop pattern.

\paragraph{R4 -- Set membership} Inside a loop, a comparison of the form \texttt{x in [literal, \ldots]} against a list literal of constants is rewritten to \texttt{x in frozenset((\ldots))}, converting an $O(n)$ membership test into $O(1)$. The rule only fires inside a loop (tracked by a nesting-depth counter) because outside a loop the one-off \texttt{frozenset} construction would not amortise.

\paragraph{R5 -- String join} The pattern of an empty-string accumulator followed by a loop that appends via \texttt{acc += expr} is rewritten to accumulate into a list and emit \texttt{acc = ''.join(buffer)}, avoiding the quadratic cost of repeated string concatenation.

As reported in Section~\ref{sec:resultados}, R2, R4, and R5 frequently \emph{regress} on HumanEval because the small input sizes do not amortise the construction of the intermediate generator, \texttt{frozenset}, or list. This is itself an informative negative result: it demonstrates concretely that a transformation can be locally idiomatic and globally counter-productive, which is precisely the contextual judgement an LLM is positioned to make and a syntactic rule is not.

\subsection{Static Feature Extraction}
The Static Analysis Module is realised as a single pass over the AST that materialises eight numerical features used both as conditioning signals for the LLM prompt and as filtering criteria for the deterministic rule optimiser. Algorithm~\ref{alg:features} sketches the procedure.

\begin{algorithm}[htbp]
\caption{Static feature extraction over the AST}
\label{alg:features}
\begin{algorithmic}[1]
\REQUIRE Source code $s$, entry-point name $e$
\ENSURE Feature vector $f$
\STATE $T \leftarrow \mathrm{ast.parse}(s)$
\STATE $f \leftarrow \{\mathit{nfun} \!\!=\!\! 0, \mathit{nloop}\!\!=\!\!0, \mathit{depth}\!\!=\!\!0, \mathit{ncall}\!\!=\!\!0,$
\STATE $\quad\quad \mathit{nrec}\!\!=\!\!0, \mathit{ncomp}\!\!=\!\!0, \mathit{typed}\!\!=\!\!\mathit{false}, \mathit{imp}\!\!=\!\!\emptyset\}$
\STATE $d \leftarrow 0$
\FOR{\textbf{each} node $n$ in pre-order traversal of $T$}
  \IF{$n$ is \texttt{FunctionDef}}
    \STATE $f.\mathit{nfun} \leftarrow f.\mathit{nfun}+1$
    \IF{$n$ has return or argument annotation}
      \STATE $f.\mathit{typed} \leftarrow \mathit{true}$
    \ENDIF
  \ELSIF{$n$ is \texttt{For} or \texttt{While}}
    \STATE $f.\mathit{nloop} \leftarrow f.\mathit{nloop}+1; \;\; d \leftarrow d+1$
    \STATE $f.\mathit{depth} \leftarrow \max(f.\mathit{depth}, d)$
  \ELSIF{$n$ is \texttt{Call}}
    \STATE $f.\mathit{ncall} \leftarrow f.\mathit{ncall}+1$
    \IF{$n.\mathit{func}$ is \texttt{Name} \AND $n.\mathit{func}.\mathit{id} = e$}
      \STATE $f.\mathit{nrec} \leftarrow f.\mathit{nrec}+1$ \quad // recursive call
    \ENDIF
  \ELSIF{$n$ is any comprehension or generator}
    \STATE $f.\mathit{ncomp} \leftarrow f.\mathit{ncomp}+1$ \quad // list/dict/set/gen
  \ELSIF{$n$ is \texttt{Import} or \texttt{ImportFrom}}
    \STATE add module name(s) to $f.\mathit{imp}$
  \ENDIF
  \STATE \textbf{after children of} \texttt{For}/\texttt{While}: $d \leftarrow d-1$
\ENDFOR
\RETURN $f$
\end{algorithmic}
\end{algorithm}

This vector serves two purposes in the pipeline. First, it is serialised into the LLM prompt as plain text (e.g.\ ``\textit{this function has 2 loops with max nesting depth 1, 5 calls of which 2 are recursive, no type annotations}''), giving the model an explicit summary of the structural shape of the input rather than forcing it to recover that information from the raw source. Second, the deterministic rule optimiser uses $f.\mathit{nrec} > 0$ as a precondition for the \texttt{lru\_cache} rule (R1) and $f.\mathit{nloop} > 0$ as a precondition for the \texttt{sum}, \texttt{join}, and \texttt{frozenset} rules (R2, R4, R5), avoiding wasted AST rewrites on functions that cannot possibly match.

\subsection{LLM Prompt and Output Parsing}
The LLM optimiser uses a fixed system--user prompt template (Listing~\ref{lst:system_prompt}) that emphasises three constraints: signature preservation, semantics preservation, and a code-only response delimited by a ` ```python ... ``` ` fence. The fence requirement is structural --- it allows the response to be machine-parsed by a single regular expression --- and is the source of the Class B failures discussed in Section~\ref{sec:error_analysis}.

\begin{lstlisting}[caption={System prompt (translated to English from the Portuguese version actually used in the experiments). The user prompt is built by appending the AST feature summary and the original source code below this template.}, label={lst:system_prompt}, language=, basicstyle=\ttfamily\scriptsize, breaklines=true]
You are an expert assistant in compilers and Python
code optimization. Given a Python function, you must
return a semantically equivalent and more efficient
version (lower execution time and/or lower memory
use). Follow these rules strictly:

1. Preserve the function signature exactly (name,
   parameters, type annotations, parameter order).
2. Preserve observable behaviour for every valid
   input.
3. Do NOT remove imports that are needed; add only
   imports strictly required by the optimised
   version (prefer the standard library).
4. Reply ONLY with the complete Python code of the
   optimised function (and any needed imports),
   inside a single fenced code block delimited by
   triple backticks: ```python ... ```.
5. Do NOT include explanations, tests, or example
   uses. Code only.
\end{lstlisting}

Algorithm~\ref{alg:validate} describes the validation harness applied to every candidate transformation. The harness is the structural backbone of the test-based mitigation strategy: by composing dynamic execution of the candidate against the official HumanEval test, a hard $10$-second wall-clock timeout via \texttt{SIGALRM}, and a typed exception channel, it converts every potential silent hallucination into one of the four failure classes catalogued in Section~\ref{sec:error_analysis}.

\begin{algorithm}[htbp]
\caption{Test-based validation harness}
\label{alg:validate}
\begin{algorithmic}[1]
\REQUIRE Candidate code $c$, test code $t$, entry point $e$, timeout $\tau$
\ENSURE \texttt{(passed, error)} pair
\STATE install \texttt{SIGALRM} handler that raises \texttt{TimeoutError}
\STATE set interval timer to $\tau$ seconds
\STATE $N \leftarrow$ fresh namespace
\STATE \textbf{enter} guarded block:
\STATE \quad \texttt{exec(compile($c$, '<llm>', 'exec'), $N$)}
\STATE \quad \textbf{if} $e \notin N$ \textbf{then return} \texttt{(false, "entry\_point absent")}
\STATE \quad \texttt{exec(compile($t$, '<test>', 'exec'), $N$)}
\STATE \quad \textbf{if} \texttt{check} $\notin N$ \textbf{then return} \texttt{(false, "check absent")}
\STATE \quad \texttt{$N$['check']($N$[$e$])} \quad // run all official assertions
\STATE \quad \textbf{return} \texttt{(true, $\bot$)}
\STATE \textbf{on} \texttt{TimeoutError}: \textbf{return} \texttt{(false, "timeout")}
\STATE \textbf{on} \texttt{AssertionError} as $a$: \textbf{return} \texttt{(false, "assertion: " + str($a$))}
\STATE \textbf{on} \texttt{Exception} as $x$: \textbf{return} \texttt{(false, type($x$) + ": " + str($x$))}
\STATE \textbf{finally}: clear interval timer; restore previous handler
\end{algorithmic}
\end{algorithm}

The benchmark module composes a reproducible workload from the very \texttt{candidate(\ldots)} calls embedded in the HumanEval test (extracted by a paren-balanced scan rather than full AST parsing of the test, which contains arbitrarily complex assertions). Reusing the test calls has three advantages over synthesising new inputs: it preserves the typical input-size distribution of the problem; it eliminates the need to author a per-problem driver; and it makes the workload deterministic for a given $(\mathit{repeats}, \mathit{workload\_multiplier})$ pair.

\subsection{Evaluation Metrics}
The evaluation considers four metrics: (i) \textbf{semantic preservation rate}, the fraction of optimized codes that pass all HumanEval tests; (ii) arithmetic, median, and harmonic \textbf{mean speedup} relative to the original version; (iii) \textbf{improvement rate}, the fraction of problems with speedup above $1.05\times$; and (iv) \textbf{regression rate}, the fraction of problems with speedup below $0.95\times$. Additionally, the distribution of rules triggered by the deterministic baseline is reported.

\subsection{Illustrative Example}
Listing~\ref{lst:original} shows a code typically found in competitive-programming datasets, and Listing~\ref{lst:otimizado} shows a transformation expected from the LLM.

\begin{lstlisting}[caption={Original code with explicit loop.}, label={lst:original}]
def sum_of_squares(n):
    total = 0
    for i in range(n):
        total = total + i * i
    return total
\end{lstlisting}

\begin{lstlisting}[caption={Optimized version suggested by the LLM.}, label={lst:otimizado}]
def sum_of_squares(n):
    # closed form: n*(n-1)*(2n-1)/6
    return n * (n - 1) * (2 * n - 1) // 6
\end{lstlisting}

This kind of algorithmic transformation would hardly be produced by a classical compiler, since it requires semantic knowledge of the underlying mathematical domain.

\subsection{Analysis of Results}

Three central observations emerge from the empirical results:

\begin{enumerate}
  \item \textbf{Limited coverage of symbolic rules.} Only 8 of 164 problems (4.9\%) trigger any rule. This quantitatively shows that exact syntactic matching (``\texttt{acc = 0; for x in iter: acc += expr}'') is excessively rigid: trivial style variations, such as the use of \texttt{enumerate} or auxiliary variables, escape detection. This brittleness mirrors the limit of peephole optimizers in classical compilers.
  \item \textbf{Regressions in locally correct transformations.} Rules R2, R4, and R5 produce semantically correct and syntactically idiomatic code that is in fact \textit{slower} in practice. This happens because the optimization decision was made without considering typical input size -- precisely the type of contextual information that is \textit{outside} the scope of symbolic rules but \textit{within} reach of an LLM capable of reasoning about amortized cost.
  \item \textbf{Massive gains via algorithmic transformation.} The two memoization cases (R1) confirm that the largest optimization lever in Python lies not in bytecode-level micro-optimizations but in algorithmic-level transformations. It is precisely at this level that LLMs show the greatest aptitude, as evidenced by recent literature \cite{DBLP:journals/corr/abs-2302-07867,DBLP:journals/corr/abs-2309-07062}.
\end{enumerate}

\subsection{Qualitative Analysis}
To concretize the discussed phenomena, we examine two representative cases drawn from Table~\ref{tab:detalhe}: \textbf{HumanEval/55} (\texttt{fib}), where rule R1 produces the second largest gain of the experiment ($151.8\times$), and \textbf{HumanEval/74} (\texttt{total\_match}), where rule R2 produces the worst observed regression ($0.36\times$).

\begin{lstlisting}[caption={Original \texttt{fib} (HumanEval/55).}, label={lst:fib_orig}]
def fib(n: int):
    if n == 0: return 0
    if n == 1: return 1
    return fib(n-1) + fib(n-2)
\end{lstlisting}

\begin{lstlisting}[caption={R1 version (\texttt{lru\_cache}) --- amortized $O(n)$.}, label={lst:fib_r1}]
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n: int):
    if n == 0: return 0
    if n == 1: return 1
    return fib(n-1) + fib(n-2)
\end{lstlisting}

The transformation in Listing~\ref{lst:fib_r1} adds a single decorator and reduces the observable complexity from $O(2^n)$ to amortized $O(n)$ per call, yielding a measured speedup of $151.8\times$. This is the kind of \emph{algorithmic} transformation a classical compiler does not perform, since it requires recognizing the function as a pure recurrence over small integers.

\begin{lstlisting}[caption={Original \texttt{total\_match} (HumanEval/74).}, label={lst:tm_orig}]
def total_match(lst1, lst2):
    l1 = 0
    for st in lst1:
        l1 += len(st)
    l2 = 0
    for st in lst2:
        l2 += len(st)
    if l1 <= l2: return lst1
    else: return lst2
\end{lstlisting}

\begin{lstlisting}[caption={R2 version (\texttt{sum()}) --- regression $0.36\times$.}, label={lst:tm_r2}]
def total_match(lst1, lst2):
    l1 = sum(len(st) for st in lst1)
    l2 = sum(len(st) for st in lst2)
    if l1 <= l2: return lst1
    else: return lst2
\end{lstlisting}

The version in Listing~\ref{lst:tm_r2} is \emph{idiomatic} in Python and would be considered superior in a code review. However, in benchmarks with small lists (typical HumanEval inputs contain 0 to 5 strings) the cost of creating and iterating over the generator expression exceeds the gain of the C-implemented \texttt{sum()}, resulting in performance 2.77 times worse. This is the paradigmatic example of a transformation whose \emph{decision} requires contextual information (typical input size, call frequency) that is outside the reach of syntactic matching -- and within reach of a language model capable of reasoning about amortized cost.

The mandatory presence of the test-based validation module is the mechanism that makes this risk acceptable: it turns silent hallucinations into detected failures, keeping effective semantic preservation close to $100\%$ at the cost of discarding between $6\%$ and $23\%$ of the LLM's outputs.

\subsection{Error Analysis: Failure Modes by Model}
\label{sec:error_analysis}

The aggregate hallucination rates of Table~\ref{tab:llm_vs_base} hide a qualitatively important asymmetry: failures across the three LLMs do not share the same character. By inspecting the \texttt{optimized\_error} field of each invalid record in the result JSON files, we partitioned the 77 LLM failures (10 from Gemini, 38 from Llama, 29 from GPT-4o-mini) into four failure classes:

\begin{enumerate}
  \item \textbf{Assertion failure (Class A)} -- the code parsed, executed, and returned a value, but the value disagreed with the HumanEval reference. This is the canonical ``hallucination'' as commonly understood: the model proposed a transformation that looks plausible but breaks the function semantically.
  \item \textbf{Empty/unparseable response (Class B)} -- the model's output could not be decoded by the regex that extracts the ` ```python ... ``` ` block, or the extracted block did not define the entry point. This is a \emph{format failure} rather than a semantic one: the LLM either returned prose, an empty block, or text the parser could not recover.
  \item \textbf{Runtime exception (Class C)} -- the code parsed and ran but raised \texttt{TypeError}, \texttt{ValueError}, \texttt{NameError}, or similar before reaching the assertion.
  \item \textbf{Timeout (Class D)} -- execution exceeded the 10\,s \texttt{SIGALRM} window, typically because the candidate transformation introduced an infinite loop or pathological complexity.
\end{enumerate}

Table~\ref{tab:error_modes} reveals a structurally important fact: \emph{Gemini's failures are exclusively true semantic hallucinations (Class A)}, whereas the bulk of Llama 70B's (71\%) and GPT-4o-mini's (55\%) failures are \emph{format failures}, i.e., responses that the wrapper code could not even parse. This has two immediate implications.

First, the headline ``$23.2\%$ hallucination rate'' for Llama is misleading: only $11/164 = 6.7\%$ of its outputs are genuine semantic errors, comparable to Gemini's $6.1\%$. The remaining $27/164 = 16.5\%$ are recoverable engineering failures. A more robust output parser (e.g., one that accepts code outside fenced blocks, falls back to AST-based extraction, or retries with a stricter system message) would close most of this gap.

Second, the semantic hallucination floor across all three models is remarkably stable at $10$--$11$ failures, suggesting that the genuine difficulty of producing a semantically equivalent transformation is determined more by the \emph{task} (a fraction of HumanEval problems involve subtle invariants that any LLM at this scale struggles to preserve) than by the \emph{model}. Identifying these task-intrinsic failures and characterising what makes them hard is a natural next step.

\subsubsection*{Class A example: silent semantic divergence}
Listing~\ref{lst:fail_classA} is a representative Class A failure from Gemini on \texttt{HumanEval/7} (\texttt{filter\_by\_substring}). The original returns the list of strings in \texttt{strings} that contain \texttt{substring}. Gemini's optimised version replaced the predicate-based filter by a list comprehension whose membership test inverted the operand order:

\begin{lstlisting}[caption={Class A failure (Gemini, HumanEval/7): membership test with operands swapped. The function compiles, runs, and returns a list; the assertion only fails on inputs where \texttt{substring} is itself a substring of one of the strings rather than the converse.}, label={lst:fail_classA}]
def filter_by_substring(strings, substring):
    # WRONG: tests `s in substring` instead of
    # `substring in s` -- semantically inverted.
    return [s for s in strings if s in substring]
\end{lstlisting}

The defect is structural: no syntax error, no runtime exception, no timeout --- only a wrong answer detected by the official assertion. This is exactly the failure mode that motivates the test-based validation harness: without an executable oracle, the transformation would silently ship.

The regex that scans for ` ```python ... ``` ` returned no match, the parser fell back to the raw text, and the validation harness rejected the candidate because \texttt{truncate\_number} was not defined in the resulting namespace.

The asymmetry between Gemini (0 Class B) and Llama 70B / GPT-4o-mini ($\geq 16$ Class B each) suggests that instruction-following discipline, not raw code-generation capability, dominates the observed gap. This is consistent with the observation that all three models successfully apply the same algorithmic transformations (Section~\ref{sec:win_distribution}) when they manage to emit any code at all.

\subsection{Win Distribution by Transformation Class}
\label{sec:win_distribution}

Symmetrically, we classified the wins (problems with measured speedup $>1.05\times$) by the type of transformation the LLM applied. Manual inspection of the top-10 improvement of each backend, sorted by speedup, allows them to be grouped into five recurring classes:

\begin{itemize}
  \item \textbf{T1 -- Memoization}: addition of \texttt{functools.lru\_cache} to a pure recursive function. Effect: $O(2^n)\!\to\!O(n)$ amortised. Examples: \texttt{fib}, \texttt{fibfib}.
  \item \textbf{T2 -- Algorithmic substitution}: replacement of an $O(n)$ or $O(n^2)$ algorithm by a known $O(\sqrt{n})$ or $O(\log n)$ alternative. Examples: \texttt{is\_prime} (trial division up to $\sqrt{n}$), \texttt{largest\_prime\_factor} (sieve / division loop), \texttt{modp} (replace manual modular exponentiation by \texttt{pow(a, b, m)}).
  \item \textbf{T3 -- Closed-form math}: replacement of an iterative computation by an analytical formula. Examples: \texttt{sum\_to\_n} ($n(n+1)/2$), \texttt{rounded\_avg} (closed-form integer sum), arithmetic-progression sums.
  \item \textbf{T4 -- Control-flow simplification}: collapsing nested conditionals or short-circuiting boolean predicates. Examples: \texttt{x\_or\_y}, \texttt{closest\_integer}, \texttt{is\_palindrome}.
  \item \textbf{T5 -- Builtin substitution}: replacing a hand-written loop or comprehension by a faster \texttt{builtin} or \texttt{stdlib} operation (e.g., \texttt{sum()}, \texttt{any()}, \texttt{set()}, \texttt{collections.Counter}).
\end{itemize}

\subsection{Comparative Case Study: \texttt{HumanEval/55} (\texttt{fib})}
\label{sec:case_study}

To make the heterogeneity tangible at the level of a single problem, we examine \texttt{HumanEval/55} (\texttt{fib}), the canonical recursive Fibonacci that yields the most dramatic gains across every back-end. Listing~\ref{lst:case_orig} reproduces the canonical solution that all four back-ends receive as input. Listings~\ref{lst:case_gem}--\ref{lst:case_gpt} show the optimisations produced by each LLM, together with the measured speedup.

\begin{lstlisting}[caption={Original \texttt{fib} (HumanEval/55) -- the same canonical solution fed to all four back-ends.}, label={lst:case_orig}]
def fib(n: int):
    if n == 0: return 0
    if n == 1: return 1
    return fib(n-1) + fib(n-2)
\end{lstlisting}

\begin{lstlisting}[caption={Gemini 2.5 Flash Lite -- adds \texttt{@lru\_cache} to the recursive function (speedup $\mathbf{157.22\times}$).}, label={lst:case_gem}]
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n: int):
    if n == 0: return 0
    if n == 1: return 1
    return fib(n-1) + fib(n-2)
\end{lstlisting}

\begin{lstlisting}[caption={Llama 3.3 70B -- same memoisation strategy, slightly noisier per-call overhead (speedup $\mathbf{122.72\times}$).}, label={lst:case_lla}]
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n: int):
    if n == 0: return 0
    if n == 1: return 1
    return fib(n - 1) + fib(n - 2)
\end{lstlisting}

\begin{lstlisting}[caption={GPT-4o-mini -- iterative formulation (no \texttt{lru\_cache}). The two-variable recurrence is asymptotically $O(n)$ but pays a constant-factor penalty (speedup $\mathbf{19.17\times}$).}, label={lst:case_gpt}]
def fib(n: int):
    if n == 0: return 0
    a, b = 0, 1
    for _ in range(n - 1):
        a, b = b, a + b
    return b
\end{lstlisting}

Three observations follow from this comparative case. First, the algorithmic insight is shared: all three LLMs recognise that an exponential-time recurrence on small integers can be reduced to linear time. The deterministic AST baseline reaches the same conclusion through its R1 rule (Listing~\ref{lst:fib_r1}). Second, the chosen \emph{implementation strategy} differs: Gemini and Llama converge on the decorator-based memoisation that the baseline also produces, while GPT-4o-mini rewrites the function iteratively. The two strategies are asymptotically equivalent but have very different constant factors --- the iterative version avoids the per-call hashing of \texttt{lru\_cache} but loses the memoisation across repeated calls of the same input. Third, the magnitude gap between Gemini ($157.22\times$) and GPT-4o-mini ($19.17\times$) on the \emph{same problem with the same strategy class} (T2) is not a difference in algorithmic capability, but in how well each model exploits the dominant cost in this particular benchmark (the test repeats the same calls under our 200-fold workload multiplier, which rewards memoisation more than asymptotic improvement). This single-problem view illustrates why aggregated comparisons of LLMs for code transformation must report both the median (which captures typical impact) and the maximum (which captures peak capability) --- the two metrics can move independently across the same model pair.

\section{Discussion: Limits and Possibilities}
\label{sec:discussao}

\subsection{Limits}
The experimental results, together with the literature review, allow us to outline the following limits:

\begin{itemize}
  \item \textbf{Absence of formal guarantees.} Neither the deterministic optimizer nor an LLM provides proofs of semantic equivalence. Correctness depends entirely on the quality of the test suite. In the experiment, the 164 HumanEval tests proved sufficient for the baseline, but real-world scenarios with partial coverage may fail to detect subtle semantic regressions.
  \item \textbf{Symbolic brittleness.} With only 4.9\% coverage, the deterministic optimizer shows that pattern-matching transformations are inherently limited in dynamic languages, where style, framework, and language-version variations multiply the possible patterns.
  \item \textbf{Sensitivity to input size.} ``Beneficial'' transformations may regress when the cost of constructing intermediate objects dominates execution time for small inputs, as observed in 5 of the 8 cases where rules were applied.
  \item \textbf{LLM hallucinations.} Language models can produce syntactically valid yet semantically incorrect code. In the experiment (Table~\ref{tab:llm_vs_base}), the observed rate ranges from $6.1\%$ (Gemini 2.5 Flash Lite, 10 failures) to $23.2\%$ (Llama 3.3 70B, 38 failures), with GPT-4o-mini in an intermediate position ($17.7\%$, 29 failures). All failures manifested as broken assertions in the official tests. This range quantitatively reinforces that (a) the test-based validation module is \emph{mandatory}, not optional, and (b) the choice of LLM has a direct impact on the resulting discard rate.
  \item \textbf{Python's intrinsic dynamism.} Mechanisms such as late binding, monkey patching, \texttt{eval}/\texttt{exec}, and the GIL remain fundamental barriers to aggressive static optimizations, whether symbolic or LLM-based.
\end{itemize}

\subsection{Possibilities}
On the other hand, both the results and the literature point to concrete possibilities:

\begin{itemize}
  \item \textbf{High-level algorithmic transformations.} The 151.8$\times$ and 615.4$\times$ speedups obtained with memoization confirm that the largest optimization potential in Python lies in transformations a classical compiler cannot infer. LLMs, trained on billions of tokens of code, can recognize algorithmic patterns and propose equivalent reformulations \cite{DBLP:journals/corr/abs-2407-02524,DBLP:journals/corr/abs-2302-07867}.
  \item \textbf{Contextual reasoning.} Unlike a symbolic rule, an LLM can take into account expected input size, the function's usage profile, and domain constraints present in the docstring, potentially avoiding the regressions observed for rules R2, R4, and R5.
  \item \textbf{Hybrid architecture.} Combining AST-based static analysis (to extract features and filter candidates) with LLM inference (to decide \textit{whether} and \textit{how} to optimize) yields a pipeline that recovers part of a compiler's rigor without losing the flexibility of a probabilistic model.
  \item \textbf{Runtime feedback.} Profiling information (\texttt{cProfile}), bytecode inspection (\texttt{dis}), and data from CPython 3.11+'s adaptive interpreter can enrich the LLM's prompt, in the spirit of self-debugging approaches that feed execution results back to the model \cite{DBLP:journals/corr/abs-2304-05128}.
  \item \textbf{Reproducibility at zero cost.} The existence of foundation models with free tiers (Gemini 2.5 Flash Lite, Llama 3.3 via Groq) makes it feasible to run the proposed pipeline in academic settings at no cost, as demonstrated in this work.
\end{itemize}

\subsection{Practical Guidance for Pipeline Designers}
\label{sec:practical_guidance}

Synthesising the empirical findings, the experimental design, and the qualitative analyses above, we distil four decision guidelines for practitioners considering an LLM-augmented optimisation pipeline for Python.

\paragraph{When the symbolic baseline is enough} If the target codebase is dominated by a small number of well-known idioms (e.g., recursive numerical functions that benefit from \texttt{lru\_cache}, hand-written summation loops, set-membership tests on small literals), a deterministic AST-rule layer is preferable to an LLM. It is free, deterministic, formally auditable, and preserves semantics by construction --- properties an LLM cannot match. The 615$\times$ \texttt{fibfib} speedup of Section~\ref{sec:resultados} was produced this way.

\paragraph{When to introduce an LLM} The deterministic baseline saturates rapidly: in our experiment it triggered on 4.9\% of HumanEval and produced no statistically significant median gain. If the desired coverage exceeds this regime, an LLM is justified. The cost is a hallucination floor (between 6\% and 23\% in our experiment) and a non-trivial computational and quota budget; the benefit is a roughly $6\times$ expansion of improvement coverage and the only configuration that produced a significant median speedup in our tests.

\paragraph{How to choose the LLM} Treat model selection as an engineering decision with an empirical answer. Run the candidate models against a representative paired benchmark (164 HumanEval problems is sufficient to detect effect-size differences of practical interest) and compare \emph{three} metrics simultaneously: hallucination rate, median speedup with bootstrap CI, and improvement coverage. The naive ranking by parameter count or release date is misleading; in our setting a 70B open-weight model was outperformed by a compact proprietary one on every aggregate metric (Table~\ref{tab:llm_vs_base}).

\paragraph{What to keep mandatory} Regardless of the chosen back-end, the test-based validation harness (Algorithm~\ref{alg:validate}) is non-negotiable. It is the mechanism that turns Class A hallucinations (Section~\ref{sec:error_analysis}) into discarded outputs rather than silent regressions. A robust output parser that minimises Class B failures is a complementary safety net that costs almost nothing to implement and recovers a non-trivial fraction of weaker-model losses (16.5\% of Llama 70B's outputs in our experiment).

\section{Threats to Validity}
\label{sec:ameacas}

Following the classical taxonomy of empirical software engineering research, we identify the following threats to the reported results.

\paragraph{Internal validity} Execution-time benchmarks are sensitive to OS noise, cache variation, and the interpreter itself. We mitigate this risk by running 200 workload repetitions in each of 5 rounds and reporting the minimum time, following the \texttt{timeit} library convention. Even so, speedups close to $1.0\times$ cannot be interpreted in isolation and were therefore grouped under the ``neutral'' category.

\paragraph{Construct validity} Semantic preservation is assessed by the HumanEval test suite. Although these tests are deliberately high-coverage for the target problem, full semantic equivalence requires formal proof, beyond the scope of this work. Locally correct transformations that rely on untested invariants may go undetected.

\paragraph{External validity} HumanEval consists of 164 small, self-contained functions with typically small inputs. This profile favors micro-benchmarks and penalizes transformations that amortize cost over large inputs (as observed in R2, R4, and R5). Generalizing the findings to production code, with classes, external dependencies, and real datasets, requires additional validation on larger and more diverse repositories -- a gap partially addressed by works such as DocAgent \cite{DBLP:journals/corr/abs-2504-08725}, which evaluate LLM-based systems directly on real GitHub repositories.

\paragraph{Model variability} LLMs are inherently stochastic, and their responses vary with the prompt, the temperature parameter, and the model's internal versions. The reported experiments use temperature = $0.2$ and the deterministic AST-rule back-end as a controlled baseline; results specific to Gemini 2.5 Flash Lite should be reproduced with a fixed seed and a frozen model version before any cross-comparison.

\paragraph{Limited dataset} The sole use of HumanEval as the experimental universe is a deliberate choice for reproducibility, but it restricts domain diversity. Complementary datasets such as PIE \cite{DBLP:journals/corr/abs-2302-07867} and Project CodeNet \cite{DBLP:journals/corr/abs-2105-12655} are natural candidates to mitigate this threat in future work.

\section{Conclusions}
\label{sec:conclusao}

This paper investigated the limits and possibilities of using language models for Python code optimization, focusing on the role of LLMs as an auxiliary component in the compilation toolchain of a dynamic language. We proposed and implemented a modular architecture (Ingestion $\rightarrow$ AST-based Static Analysis $\rightarrow$ Optimization $\rightarrow$ Validation $\rightarrow$ Benchmark) operating on the public HumanEval dataset (164 problems).

The empirical results from the paired execution over the 164 HumanEval problems, comparing the deterministic AST-rule optimizer and three LLMs from distinct families (Gemini 2.5 Flash Lite, Llama 3.3 70B via Groq, and GPT-4o-mini via GitHub Models), revealed five main findings:

\begin{enumerate}
\item \textbf{Formal guarantee vs.\ coverage is a real, measurable trade-off.} The baseline preserves semantics in $100\%$ of cases but improves only $9.1\%$ of problems; the LLMs preserve between $76.8\%$ and $93.9\%$ and improve between $27.4\%$ and $54.3\%$.

\item \textbf{Heterogeneity across LLMs is high and \emph{matters}.} Improvement coverage varies $2\times$ across the three LLMs ($27.4\%$ Llama vs.\ $54.3\%$ Gemini), and the hallucination rate varies $4\times$ ($6.1\%$ Gemini vs.\ $23.2\%$ Llama). The choice of model is not neutral.

\item \textbf{Only one of the three LLMs produces a statistically significant median gain.} The 95\% bootstrap CI for the median speedup excludes $1.0$ only for Gemini ($[1.071;~1.220]$); Llama and GPT-4o-mini have CIs that cross $1.0$, with Llama in fact below it ($0.976$).

\item \textbf{Extreme algorithmic gains are achievable by every LLM.} Memoization, closed-form formulas, \texttt{pow(a,b,m)}, and prime sieves were rediscovered by all models with speedups between $100\times$ and $300\times$. The difference lies in the frequency of correct application, not in the pointwise capability.

\item \textbf{Test-based validation is an effective containment mechanism.} Across all LLMs, $100\%$ of hallucinations were caught by the official HumanEval suite. Without the validation module, the user would receive between $6\%$ and $23\%$ of semantically incorrect code.
\end{enumerate}

These results refute the simplistic thesis that ``LLMs beat the baseline'' and establish a more precise and useful one: \emph{symbolic approaches are necessary but insufficient; LLMs expand the optimization frontier at the cost of formal guarantees; and the magnitude of this gain depends strongly on the chosen model}. Integrating LLMs as a high-level reasoning component in a pipeline with mandatory semantic validation and model selection empirically validated on the target domain therefore constitutes an empirically validated direction for overcoming the limits imposed by language dynamism.

As future work, we plan to: (i) integrate Retrieval-Augmented Generation (RAG) \cite{DBLP:journals/corr/abs-2005-11401} with the PIE dataset \cite{DBLP:journals/corr/abs-2302-07867} as a source of few-shot examples, with the expectation of reducing the high hallucination rate observed in the weaker LLMs (up to $23.2\%$ in Llama 70B); (ii) incorporate CPython 3.11+ bytecode feedback and profiling reports as additional prompt context, in the spirit of self-debugging approaches \cite{DBLP:journals/corr/abs-2304-05128}; (iii) evaluate generalization to other, more complex datasets (Project CodeNet Python800, MBPP \cite{DBLP:journals/corr/abs-2108-07732}, real GitHub repositories) and to code-specialized LLMs such as DeepSeek-Coder \cite{DBLP:journals/corr/abs-2401-14196}, StarCoder~2 \cite{DBLP:journals/corr/abs-2402-19173}, and Code Llama \cite{DBLP:journals/corr/abs-2308-12950} under the same paired-comparison protocol; (iv) implement a self-refine loop \cite{DBLP:journals/corr/abs-2303-17651} in which validation failures are returned to the LLM as context for a new attempt, aiming to recover part of the hallucinations; (v) investigate \textbf{why} heterogeneity across LLMs is so large -- particularly, whether the gap between Gemini ($6.1\%$ hallucination) and Llama 70B ($23.2\%$) stems from model size, training data, alignment techniques, or prompt tuning; and (vi) explore a multi-agent architecture inspired by DocAgent \cite{DBLP:journals/corr/abs-2504-08725}, in which agents specialized in analysis, transformation, and verification cooperate through an orchestrator, with dependency-aware traversal of the program's call graph.

\paragraph{Expected contributions} In summary, this work contributes: (1) a critical, reproducible, and \emph{multi-model} evaluation of the use of generative AI for code optimization in a dynamic language, comparing three LLMs from distinct providers and families; (2) the quantitative identification of the real limits of symbolic pattern-based approaches over AST (only $4.9\%$ coverage on HumanEval, with no statistically significant median gain); (3) empirical evidence of \emph{strong heterogeneity across LLMs} for the code-optimization task (hallucination varying $4\times$, coverage varying $2\times$, only one of the three models reaching statistical significance in median speedup); and (4) guidelines for the safe use of LLMs in optimization pipelines -- notably, the obligation of test-based semantic validation, the need for empirical model selection on the target domain (one cannot simply assume a ``modern'' LLM works), and the adoption of a verification mesh inspired by systems such as DocAgent \cite{DBLP:journals/corr/abs-2504-08725}.

\section{Reproducibility and Artefacts}
\label{sec:reproducibility}

To support independent verification and reuse, the entire pipeline, dataset, raw results, and figure-generation scripts are publicly available. This section documents the experimental environment and the steps needed to reproduce every number reported in the paper.

\subsection{Experimental Environment}
All experiments were executed on CPython~3.11 over Linux. The deterministic baseline is fully reproducible and requires no external service. The three LLM back-ends were accessed through free-tier APIs: Google AI Studio (Gemini), Groq (Llama~3.3~70B), and GitHub Models (GPT-4o-mini). All inference calls used \textit{temperature} $= 0.2$ and \textit{max\_output\_tokens} $= 2048$, with a fixed random seed (\texttt{42}) for the problem ordering. Because LLM inference is non-deterministic even at low temperature, exact per-problem speedups may vary slightly across runs; the aggregate statistics (medians, confidence intervals, hallucination rates) are stable across repetitions.

\subsection{Software Components}
The pipeline comprises five interchangeable Python modules totalling approximately 1{,}366 lines of code:
\begin{itemize}
  \item \texttt{pipeline.py} -- the orchestrator exposing a command-line interface with the \texttt{-{}-backend} switch (\texttt{rule\_based}, \texttt{gemini}, \texttt{groq}, \texttt{github\_models}).
  \item \texttt{optimizer.py} -- the multi-provider LLM client. All providers expose an OpenAI-compatible interface or a simple REST endpoint, enabling transparent back-end interchange. Exponential retry (up to 7 attempts, backoff up to 60\,s) absorbs the transient 429/5xx errors common on free tiers.
  \item \texttt{rule\_optimizer.py} -- the deterministic AST-rule optimiser implementing R1 (\texttt{lru\_cache}), R2 (\texttt{sum()}), R4 (\texttt{frozenset}), and R5 (\texttt{join}).
  \item \texttt{bench\_utils.py} -- the validation harness (Algorithm~\ref{alg:validate}) and the benchmark routine.
  \item \texttt{generate\_figures.py} / \texttt{generate\_comparison.py} -- the \texttt{matplotlib} scripts that produce every figure in this paper directly from the result JSON files.
\end{itemize}

\subsection{Reproduction Recipe}
The baseline is reproduced with a single command requiring no API key:
\begin{center}
\texttt{\scriptsize python3 pipeline.py -{}-backend rule\_based -{}-n 164}
\end{center}
Each LLM back-end is reproduced by exporting the corresponding free-tier key and selecting the back-end, e.g.:
\begin{center}
\texttt{\scriptsize python3 pipeline.py -{}-backend gemini -{}-n 164}
\end{center}
Each run emits a JSON file with one record per problem, containing the extracted AST features, the original and optimised execution times, the validity flag, the typed error string, and the measured speedup. The aggregate tables (Tables~\ref{tab:agregado}--\ref{tab:agreement}) and all figures are regenerated deterministically from these JSON files, so a reviewer can recompute every reported statistic without re-invoking any LLM. The four result files produced for this paper (one per back-end, $164$ records each) are included in the repository, ensuring that the analysis is verifiable even without API access.

\subsection{Dataset Provenance}
The HumanEval dataset \cite{DBLP:journals/corr/abs-2107-03374} is the unmodified public release distributed by OpenAI under the MIT license, redistributed unchanged as \texttt{HumanEval.jsonl.gz}. No problem was filtered, edited, or excluded: all 164 problems were processed by every back-end, and the handling of the 8--9 problems whose execution time fell below the clock resolution is documented explicitly in the footnotes of Tables~\ref{tab:agregado} and~\ref{tab:llm_vs_base}.
